# wexport 2.0 — plan

2.0 adds **iPhone backups** to the ones the tool already opens. Nothing else changes: it stays a
command-line tool, the archive format stays the same, and the packaging stays what 1.0 ships — one
archive per platform for the CLI.

The graphical application and the portable packaging are written down here as **later work**
(§7), not as part of 2.0. `docs/implementation-plan.md` remains the contract for the pipeline and the
archive; this document adds a second source of data to it.

---

## 1. What 2.0 is

| | 1.0 (shipped) | 2.0 |
|---|---|---|
| Data sources | Android `crypt15`, 64-digit key | the same, **plus iPhone local backups** |
| Interface | CLI | CLI, unchanged flags |
| Packaging | `.tar.gz` (Linux), `.zip` (Windows) | unchanged |
| Archive format | one folder per chat, `file://` viewer | unchanged — a chat from either phone becomes the same kind of folder |

One pipeline, one archive, two adapters. The archive side (`archive`, `chunks`, `media`, the viewer)
does not learn that iPhone exists.

---

## 2. What an iPhone backup is, and what 2.0 can open

A local backup made by Finder or iTunes is a folder of hashed files plus a `Manifest.db` that maps each
file to a domain and a path. WhatsApp's data lives in its app group
(`group.net.whatsapp.WhatsApp.shared`): `ChatStorage.sqlite` (Core Data), the media under
`Message/Media/…`, and the contacts database. The message schema is **nothing like** Android's
`msgstore.db`: `ZWACHATSESSION`, `ZWAMESSAGE`, `ZWAMEDIAITEM`, `ZWAGROUPMEMBER` and friends.

| How the data is held | 2.0 |
|---|---|
| Local backup, **not encrypted** (Finder/iTunes, "Encrypt local backup" off) | **opens** — no key involved |
| An already-extracted app container or `ChatStorage.sqlite` | **opens** |
| Local backup, **encrypted** with the Apple backup password | not in 2.0: needs Apple's keybag, a component of its own (§7.2) |
| **iCloud** backup | never offline: it needs the Apple account and the network. Out. |
| WhatsApp's E2EE key (64 digits / passkey) | irrelevant here: on iPhone it protects the **cloud** copy, not a file on disk |

So the 2.0 message becomes: *Android needs the 64-digit key; an iPhone needs a local backup that is
not encrypted.* The README's "Android only" and the usage page's table change in the same milestone
that ships it, not before.

## 3. Architecture

```
discover  ──►  Source::Android(Inputs)  ──►  msgstore (existing)  ─┐
          └─►  Source::Ios(IosInputs)  ──►  ios      (new)         ├─►  Message ─► archive (unchanged)
                                                                   ┘
```

- **`discover`** detects the source instead of assuming `crypt15`: a copied phone folder, a
  `Manifest.db` backup directory, or a `ChatStorage.sqlite`. The existing Android discovery is
  unchanged behind the detection; the CLI takes the same argument.
- **`src/ios.rs`** is the second schema adapter. It opens `ChatStorage.sqlite` read-only, resolves the
  columns by probing the schema — the same rule as Android: names are discovered, never guessed from
  an app version — and produces the existing `Chat`/`ChatStat`/`Message` values. Everything downstream
  (chunking, media placement, thumbnails, the viewer) is untouched.
- **Media** resolves from the app group: `ZWAMEDIAITEM.ZMEDIALOCALPATH` is a relative path inside the
  backup, and the same content-addressed placement applies. A missing file is the same first-class
  "missing" state it already is.
- **Time**: Core Data stores seconds since 2001-01-01, while the archive stores Unix milliseconds. The
  conversion lives in `ios.rs` and nowhere else, and a test pins it to both a winter and a summer date
  so an epoch slip cannot pass.
- **CLI**: the flags do not change. `-k` stays the Android key; on an iPhone backup it is not needed,
  and asking for it would be a bug. The chat codes, the ordering and `-t ZONE` behave exactly as they
  do for Android.

## 4. Testing

- **A synthetic iPhone fixture in the repository**, generated by a script next to the Android one: a
  `ChatStorage.sqlite` with a handful of chats, groups with senders, media rows, a call, a location,
  a vCard, a deleted and an edited message, and a `Manifest.db` backup around it. Committed, like
  `tests/fixtures/synthetic/phone`.
- **Unit tests on the adapter**: each Core Data field mapped, the 2001 epoch, group authors, the media
  path, missing media, a schema with a renamed column.
- **End-to-end**: the same chats built from the iOS fixture and from the Android fixture produce
  archives that pass the same contract tests — folder names, record shape, frozen stamps, a rebuild
  that changes nothing. The golden chunk stays the Android one; the iOS side gets its own.
- **A real backup, outside the repository**, run by hand on a volunteer's iPhone backup, the way the
  Android real-backup test works today.
- The gates do not change: `scripts/gate.sh` on a push, `scripts/gate-release.sh` before a tag.

| # | Work | Acceptance |

| M5 | Validation on a real backup, fixes, 2.0 tag and release | the three-command path works on a real iPhone backup |

Each milestone is committed on its own and pushed; the release gate runs once, before the 2.0 tag.

## 6. Risks

| Risk | Effect | Mitigation |
|---|---|---|
| The Core Data schema differs between iOS versions | the adapter reads nothing, or the wrong column | probe the schema and fail with the column names, as Android does; a fixture per layout we can get |
| Media lives in more than one place (`Message/Media`, `Library/Media`) | missing media in the archive | resolve both and test both in the fixture |
| Core Data timestamps | dates off by 30 years | one conversion function, pinned by tests on winter and summer dates |
| Encrypted local backups are common | "it does not open my backup" | the error names the fix ("turn off Encrypt local backup and make a new one"), §7.2 |
| A 4 GB `ChatStorage.sqlite` | memory | the adapter streams like the Android one; the archive writes per batch |
| No iPhone among the maintainers | untested code shipped | the real-backup run in M5 is a condition of the release, not an optional check |
| The product's one-line identity ("Android, 64-digit key") | documentation contradicts itself | changed in M4, in one place: the usage page's table, and the README's box |

## 7. Later, deliberately not now

### 7.1 The graphical application

A window over the same pipeline (folder → key → chats → build → open the archive) and the CLI shipped
inside the same artifact. The prerequisite is the refactor of `ui.rs` from printing to emitting events,
then a toolkit (Tauri recommended: the viewer is already HTML), then signing and notarization. It is a
project of its own and it is not in 2.0.

### 7.2 Encrypted iPhone backups

Opening a backup where "Encrypt local backup" is on means implementing Apple's keybag (PBKDF2, class
keys, AES-CBC per file) — a component with its own failure modes, and one that touches a user's Apple
backup password. Not in 2.0; 2.0 says clearly what to do instead (make an unencrypted local backup).

### 7.3 Packaging for macOS and Windows, portable Linux

When the GUI arrives, one artifact per platform, and the constraint decides the format:

- **Linux: AppImage** — one file, double click, nothing installed. Built with the current
  [`type2-runtime`](https://github.com/AppImage/type2-runtime), statically linked against musl and FUSE,
  so `libfuse2` is not required on the target; that is proven by running the artifact in a container
  without `libfuse2`, not assumed. Built on an old base so the glibc floor stays low.
- **macOS: `.app` in a signed, notarized `.dmg`.** An unsigned downloaded `.app` is quarantined by
  Gatekeeper; notarization needs an Apple Developer ID (~99 USD/year).
- **Windows: portable `.exe`** (NSIS portable mode), signed with Authenticode if the certificate is
  bought.

An AppImage is an ELF: it cannot be the macOS or the Windows artifact, and no format is universal
across the three systems. One artifact per platform, the same steps for the user.
